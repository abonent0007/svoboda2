# DPI-4A — ByeDPI Strategy Lab

## Цель

Создать лабораторную среду для тестирования и сравнения стратегий обхода DPI на основе проверенного клиента `ciadpi`/`byedpi`. Проект Svoboda 2.0 предоставляет механизм хранения и переключения профилей стратегий, но сам движок `ciadpi` не встроен в приложение — этот лабораторный каталог предназначен для документирования и экспериментального использования.

## 1. Контекст проекта

### 1.1. Существующие компоненты Svoboda 2.0

- **VPN-транспорт**: GoBackend + AmneziaWG/WARP
- **Хранение настроек**: SecureConfigStorage (AES-256-GCM, Android Keystore)
- **Управление состоянием**: ConnectionStateRepository, ConnectionStateReducer
- **Переподключение**: ReconnectCoordinator (backoff 2/5/10/20/40/60с с джиттером)
- **Фильтрация трафика**: SplitTunnelManager (ALL / ONLY_SELECTED / ALL_EXCEPT_SELECTED)
- **DNS/IPv6**: Per-profile настройка
- **Android Lifecycle**: P3.10 Stage B (onRevoke, Always-on, Foreground Service)
- **Профили**: 74 seed-конфига WARP, OwnServerStore, ProfileHistoryStore

### 1.2. ByeDPI / ciadpi — отдельный проект

- `ciadpi` / `byedpi` — проект `hufrea/byedpi` на GitHub
- CLI-синтаксис параметров — не Lua-стратегия Zapret2
- Разрабатывать отдельно от оригинальных стратегий Zapret2
- Параметры передавать массивом `argv`, а не как shell-строку

### 1.3. Важные особенности

- ROOT нет и не предполагается
- Не создавать второй Android VpnService
- Не ломать AWG, WARP, GoBackend
- Не ломать SecureConfigStorage
- Не ломать ReconnectCoordinator
- Не менять SplitTunnel и DNS/IPv6
- Все стратегии документировать, не рекламировать как гарантированно работающие без тестирования

## 2. Каталог стратегий ByeDPI (ByeDPI Strategy Catalog)

### 2.1. BDP-00 — Контрольная (оригинал)

```
-Ku -a3 -An -Kt,h -d1 -s0+s -d3+s -s6+s -d9+s -s12+s -d15+s -s20+s -d25+s -s30+s -d35+s -An
```

- Статус: **Эталон**, не изменять при экспериментах
- Цель: базовая линия для сравнения

### 2.2. BDP-01 — Разреженная (Sparse)

```
-Ku -a3 -An -Kt,h -d1 -s0+s -d5+s -s11+s -d18+s -s27+s -d37+s -An
```

- Снижение密度 точек обработки
- Редче чередование split/disorder
- Цель: тест минимальной 밀密度

### 2.3. BDP-02 — Плотная начальная (Dense Early)

```
-Ku -a3 -An -Kt,h -d1 -s0+s -d2+s -s4+s -d6+s -s9+s -d13+s -s18+s -d24+s -s31+s -An
```

- Больше точекSplit в начале SNI
- Чередование split/disorder с шагом 2
- Цель: проверка начала с активного split

### 2.4. BDP-03 — Split First (Split First)

```
-Ku -a3 -An -Kt,h -s0+s -d2+s -s5+s -d8+s -s12+s -d17+s -s23+s -d30+s -An
```

- Начинается с split, затем чередует disorder
- Меняет порядок относительно исходной
- Цель: эффект от порядка операций

### 2.5. BDP-04 — Disorder Dominant (Disorder Dominant)

```
-Ku -a3 -An -Kt,h -d1 -s0+s -d3+s -d5+s -d8+s -d12+s -d17+s -s23+s -d30+s -An
```

-Больше disorder операций, меньше split
- Меняет баланс между split и disorder
- Цель: влияние Disorder-only подхода

### 2.6. BDP-05 — Split Dominant (Split Dominant)

```
-Ku -a3 -An -Kt,h -d1 -s0+s -s3+s -d6+s -s9+s -s13+s -d18+s -s24+s -s31+s -An
```

- Основной упор на последовательное разделение
- Mеньше disorder вызовов
- Цель: проверка Split-dominant подхода

### 2.7. BDP-06 — Split Only (Только split)

```
-Ku -a3 -An -Kt,h -s0+s -s2+s -s5+s -s9+s -s14+s -s20+s -s27+s -s35+s -An
```

- Контрольный вариант без disorder
-纯粹 split-степени
- Цель: упор только на split

### 2.8. BDP-07 — Disorder Only (Только disorder)

```
-Ku -a3 -An -Kt,h -d1 -d3+s -d6+s -d10+s -d15+s -d21+s -d28+s -d36+s -An
```

- Контрольный вариант без ordinary split
- Только disorder операции
- Цель: проверка Disorder-only

### 2.9. BDP-08 — Позднее SNI (Late SNI)

```
-Ku -a3 -An -Kt,h -d1 -s0+s -d6+s -s13+s -d21+s -s30+s -d40+s -An
```

- Редкая обработка ближе к концу SNI
- Другие позиции split/disorder
- Цель: эффект от позднего разделения

### 2.10. BDP-09 — Альтернативная последовательность (Alternative Sequence)

```
-Ku -a3 -An -Kt,h -d1 -s1+s -d4+s -s8+s -d13+s -s19+s -d26+s -s34+s -An
```

- Меняет чередование и смещения относительно исходной
- Новый порядок позиций
- Цель: альтернативная организация

### 2.11. BDP-10 — UDP Low (UDP Low)

```
-Ku -a1 -An -Kt,h -d1 -s0+s -d3+s -s6+s -d9+s -s12+s -d15+s -s20+s -d25+s -s30+s -d35+s -An
```

- Меньшее количество UDP fake-пакетов
- `-a1` вместо `-a3`
- Все остальное сохраняется
- Цель: влияние количества UDP

### 2.12. BDP-11 — UDP High (UDP High)

```
-Ku -a4 -An -Kt,h -d1 -s0+s -d3+s -s6+s -d9+s -s12+s -d15+s -s20+s -d25+s -s30+s -d35+s -An
```

- Большее количество UDP fake-пакетов
- `-a4` вместо `-a3`
- Все остальное сохраняется
- Цель: проверка высокой нагрузки UDP

### 2.13. BDP-12 — Раздельная обработка TLS и HTTP (Separate TLS and HTTP)

```
-Ku -a3 -An -Kt -d1 -s0+s -d3+s -s6+s -d9+s -s12+s -d15+s -s20+s -d25+s -s30+s -d35+s -An -Kh -d1 -s0+h -d3+h -s6+h -d9+h -s12+h -d15+h -s20+h -d25+h -s30+h -d35+h -An
```

- Разделяет обработку SNI и Host
- Для TLS: `+s` (SNI pattern)
- Для HTTP: `+h` (Host pattern)
- Оригинальный профиль использует общую последовательность `+s`
- Особенно интересен для исследования различий TLS SNI vs HTTP Host структур
- Не следует считать улучшением без проверки обоих типов соединений

## 3. Правила работы с каталогом

### 3.1. Нумерация и версионирование

- Все профили идентифицируются по BDP-XX номеру
- BDP-00 — Baselines, never overwrite
- Остальные профили — экспериментальные варианты
- Каталог версионировать отдельно от основного приложения

### 3.2. Валидация параметров

Каждый профиль должен пройти валидацию:

- `-K` флаг: фильтр UDP, допустимые значения `-a1`, `-a3`, `-a4`
- `-A` группа: `-An` означает отсутствие триггера ошибки для этой группы
- Последовательность `-s` (split) и `-d` (disorder): позиции должны быть в возрастающем порядке
- `+s` (смещение SNI), `+h` (смещение Host)
- Позиции должны следовать правилам ByeDPI/cliadpi
- Неизвестные параметры сохранять, не удалять молча
- Аргументы хранить как массив `argv`, а не исполнять как shell-строку

### 3.3. Порядок тестирования

Тестировать только один профиль за раз, в следующем порядке:

1. BDP-00 (контрольная)
2. BDP-01–03 (плотность и распределение)
3. BDP-04–07 (влияние disorder)
4. BDP-08–09 (позиция точек разбиения)
5. BDP-10–11 (количество UDP fake)
6. BDP-12 (раздельная обработка TLS/HTTP)

### 3.3.1. Для каждой стратегии проверять:

- запуск ciadpi
- локальный SOCKS5 proxy
- TUN-трафик
- TCP 443
- UDP/QUIC (отдельно!)
- YouTube (открытие, поиск, воспроизведение, Shorts)
- Telegram (подключение, сообщения, медиа, файлы, звонки)

### 3.4. Условия тестирования

- Тестировать только один профиль за раз
- Не изменять остальные компоненты приложения
- Проводить тесты отдельно на Wi-Fi и LTE
- Условия должны быть одинаковыми для сравнения
- Успешное HTTPS TCP не означает, что QUIC работает
- Успешное YouTube не означает, что работают Telegram-звонки

### 3.5. Формат результатов

Сохранять для каждой стратегии:

- запуск движка ciadpi
- установление соединения
- TCP success (да/нет)
- UDP/QUIC success (да/нет)
- YouTube success (да/нет)
- Telegram success (да/нет)
- среднее время подключения
- TTFB (Time to First Byte)
- throughput (скорость передачи)
- ошибки (если есть)
- условие сети (Wi-Fi / LTE)

### 3.6. Автовыбор (планируется)

На этом этапе — ручной тест.

Можно реализовать ранжирование протестированных профилей.

Сравнивать:
- успех YouTube
- успех Telegram
- TCP
- UDP/QUIC
- стабильность
- задержка
- скорость

Лучший профиль хранить отдельно для Wi-Fi и LTE.

BDP-00 всегда сохранять как fallback.

### 3.7. Ограничения интеграции

- Не менять AWG
- Не менять WARP
- Не менять GoBackend
- Не создавать второй VpnService
- Не ломать текущий SplitTunnel
- Не ломать SecureConfigStorage
- Не переписывать ReconnectCoordinator
- Не менять оригинальную BDP-00
- Не смешивать ByeDPI-профили с Zapret2 Lua

## 4. Интеграция в Svoboda 2.0

### 4.1. Структура хранения

```
bye_dpi_strategy_catalog.json
или
bye_dpi_strategies.db (SQLite)
```

Каждый профиль хранить как запись с полями из Раздела 2.

### 4.2. Экран управления стратегиями

Добавить в настройки приложения:

- список доступных стратегий BDP-00 через BDP-12
- переключение стратегии
- статус последнего теста
- кнопка "Тестировать сейчас"
- отображение результатов (YouTube/Telegram/TCP/UDP)

### 4.3. Механизм переключения

При выборе стратегии:

1. Сохранять выбор в `SecureConfigStorage`
2. Перезапускать VPN-соединение с новыми параметрами
3. Запускать тестирование в фоне (пояснить, что это экспериментальный режим)
4. Показывать результат после завершения теста

### 4.3. Важное примечание

Приложение уже имеет рабочий VPN-клиент (AWG/WARP). ByeDPI-стратегии работают через локальный SOCKS5 proxy, который настраивается отдельно от основного туннеля. Интеграция требует понимания того, как SOCKS-режим взаимодействует с существующим GoBackend.

## 5. Какой результат я ожидаю

Моя цель — не просто получить 13 стратегий с параметрами. Хочу, чтобы в «Свободе 2.0» появился механизм:

- хранения проверенной исходной стратегии (BDP-00)
- быстрого переключения экспериментальных вариантов
- сравнивания работы на разных операторах

**BDP-00 остаётся эталоном.** Ни одна экспериментальная стратегия не должна автоматически заменять её до подтверждения результата на реальном устройстве.

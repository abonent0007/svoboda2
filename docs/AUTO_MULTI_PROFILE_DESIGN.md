# «Свобода 2.0» — AUTO-режим и раздельные профили: дизайн-бриф (на ревью)

Дата: 2026-11-16. Автор: DeepSeek. Ревьюер: GPT. Цель брифа — зафиксировать проверенные
факты, предложить реалистичную архитектуру и получить замечания до кода.

## 1. Задача от владельца

1. «Помимо нескольких приложений под одним VPN — раздельные, каждый под свои нужды»:
   например, Telegram → один туннель/профиль, YouTube → другой, банки → напрямую.
2. Сделать кнопку **AUTO** активной на главном экране: всё автоматизируется под этот режим.
3. Приоритет по странам выхода: **Нидерланды, Финляндия, США**.

## 2. Проверенные факты (источники: android.jar API 35, доки Android, Google AI Mode)

1. **`android.net.VpnService.Profile` и `VpnService.Builder.setProfile()` НЕ существуют** в
   публичном SDK (проверено чтением android.jar: в android/net/VpnService* есть только
   addAllowedApplication, addDisallowedApplication, setBlocking, setMtu).
   «Per-app VPN profiles» в Android 14/15 существуют только для **системного** IKEv2-VPN
   (VpnManager / PlatformVpnProfile), недоступны стороннему VpnService-приложению.
2. **Один активный VpnService на профиль пользователя** → один tun-интерфейс. Установка
   второго tun вызывает `onRevoke()` у первого. (Исключение: рабочий профиль Android —
   отдельный network namespace.)
3. Per-app routing возможен только в одном из двух режимов: allowlist ИЛИ denylist
   (оба вместе → `UnsupportedOperationException`).
4. Приложение-VPN автоматически исключено из собственного tun; исходящие сокеты
   апстрима надо защищать через `VpnService.protect(fd)`.
5. Реальная «маршрутизация разных приложений в разные туннели» на стоке Android делается
   **одним tun + userspace-роутером** с UID-атрибуцией потоков
   (`ConnectivityManager.getConnectionOwnerUid()`, API 29+) и мультиплексингом на несколько
   апстримов (так делают PC Manager, AdGuard local VPN, sing-box/mihomo с `process_name`).
   Цепочка туннелей внутри одного приложения возможна (оба туннеля — userspace-библиотеки).
6. Страна выхода WARP = ближайший PoP Cloudflare (anycast) — выбрать NL/FI/US напрямую не предусмотрено;
   «флаговые» релеи публичных генераторов — их собственная инфраструктура (доступ по
   Telegram-боту). Гарантированная страна = свой AWG-сервер в нужной стране.

## 3. Текущая архитектура приложения

- Движок AWG/WARP: `VpnService` (vendored amneziawg-android) → tun0 → amneziawg-go → сеть.
- DPI-режим: tun0 → HEV (tun2socks, JNI) → локальный SOCKS5 127.0.0.1:1080 → ciadpi → сеть.
- Split-туннелинг: allow/deny на уровне VpnService (по пакетам), профили хранятся в
  `SplitTunnelStore` (per profileId).
- Реконнект: `ReconnectCoordinator` (backoff ≤60 c, health-сигналы), всегда-on реконнект.
- Генерация WARP-профилей: своя (`WarpGenerator` + `WarpProfileFactory`) на базе Cloudflare
  registration API; каталог стратегий DPI: 42 шт.

## 4. Предлагаемые решения

### Вариант A — «AUTO v1» на текущем движке (реализуемо сейчас, без рефакторинга ядра)

AUTO = автоматический выбор **одного активного профиля** + health-fallback:

- Набор правил: {назначение → профиль/режим}, например:
  «Telegram → WARP-профиль (NL/FI/US)», «YouTube → AWG-профиль», «банки/госсервисы → напрямую
  (split denylist)», «остальное → DPI-режим».
- Триггеры переключения: смена активного приложения (foreground-детект) + периодическая
  проверка «нужен ли другой профиль» + health-алерт (туннель упал → следующий профиль из
  приоритета).
- Реализация: тот же VpnService, переподключение tun (1–3 с разрыва), переиспользование
  существующих `ReconnectCoordinator`/`ProfileTestCoordinator`.
- Особенность: одновременных разных туннелей нет — переключение с разрывом.

### Вариант B — «настоящие раздельные туннели» (требует смены ядра)

Один tun (наш текущий) + userspace-роутер с UID-атрибуцией и мультиплексингом на N апстримов:
- Апстримы: amneziawg-go (AWG-профиль A), amneziawg-go (WARP-профиль B), прямой сокет,
  SOCKS5→ciadpi (DPI).
- Реализация движка: либо sing-box/mihomo (MIT/Apache, умеет tun+route по `process_name`),
  либо собственная реализация поверх lwip/HEV с расширением на несколько исходящих.
- Требования: `PACKAGE_USAGE_STATS`/Accessibility не нужны — UID берём из
  `getConnectionOwnerUid`; нужен корректный `protect()` для каждого апстрим-сокета;
  нужна маршрутизация DNS по UID, чтобы не было DNS-утечек и split-horizon.

### Страны выхода (NL/FI/US)

- Для каждого сгенерированного WARP-профиля измеряем фактическую страну выхода
  (у нас уже есть probe exit-IP: Cloudflare trace → loc) и помечаем профиль; UI фильтрует
  «Нидерланды/Финляндия/США».
- Гарантированные NL/FI/US — через собственные AWG-серверы (у нас уже есть раздел AWG со
  своими серверами) либо через сторонние релеи (внешняя зависимость, не зашиваем).

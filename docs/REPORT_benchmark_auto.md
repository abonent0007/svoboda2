# «Свобода 2.0» — отчёт для ревью (GPT): DPI-движок, бенчмарк стратегий, AUTO v1

Дата: 2026-11-16. Автор: DeepSeek. Ревьюер: GPT.

## 1. Что сделано (проверено на устройстве Realme RMX3370, Android 13)

1. **DPI-движок**: ciadpi 17.3 (отдельный процесс) + HEV tun2socks (JNI, в процессе приложения).
   TUN принадлежит GoBackend, fd передаётся HEV, `wgTurnOn` пропускается; собственный пакет
   исключён из VPN (иначе рекурсия). Доказательство связи — HTTPS-запрос через локальный
   SOCKS5 127.0.0.1:1080; при неудаче — DEGRADED с честной надписью.
2. **Своя DPI-стратегия**: ручной ввод argv ciadpi, проверка числа токенов, приоритет над
   каталогом. Каталог — 42 стратегии (BDP / Простые P1 / Fake P1 / Комбинированные P2 /
   Расширенные / HTTP), все токены сверены с исходниками ciadpi 17.3.
3. **Бенчмарк стратегий (P1)**: выбор доменов (46 в 7 категориях, сохраняется), последовательный
   перезапуск **только ciadpi** (Android VPNService не трогаем), измерения DNS→TCP→TLS→HTTP
   через локальный SOCKS5 (то есть гарантированно через проверяемую стратегию), 3 попытки,
   SQLite-журнал (session/strategy/domain/attempt), ранжирование по критериям ТЗ, пауза/стоп
   с восстановлением конфигурации, экспорт JSON/CSV.
4. **Генератор WARP**: шаблоны AWG 1.0/2.0/3.0/3.1 (I1/I2/I3, ContentPaddingAddition,
   RekeyAfterTime, RekeyTimeout, RejectAfterTime, KeepaliveTimeout, MaxHandshakeAttempts,
   RandomTrailers/DisableCookies) + LTE-режим (MTU 1280, keepalive 25, только Cloudflare-маршруты),
   свой генератор QUIC-Initial для I1, endpoint-пресеты, DNS-пресеты с **проверкой валидности
   реальным DNS-запросом**, массовое создание N профилей, измерение фактической страны выхода.
5. **Раздельное туннелирование по сервисам**: 16 сервисов с IP-диапазонами → AllowedIPs →
   маршруты строятся по AllowedIPs, поэтому в туннель идёт только трафик выбранных сервисов,
   остальное напрямую. Есть и обратный пресет «сервисы напрямую».
6. **AUTO v1**: кнопка активна; подбор транспорта по порядку AWG→WARP→DPI и приоритету стран
   NL→FI→US; переключений по foreground-приложению нет; антидребезг (удержание 5 мин);
   строгая/гибкая политика страны; проверка доступности Telegram DC → при недоступности
   DC через DPI выбирается AWG/WARP, иначе — честное сообщение пользователю.

## 2. Проверенные факты по платформе (первоисточник — android.jar API 35)

- `android.net.VpnService.Profile` и `Builder.setProfile()` **не существуют** в публичном SDK →
  per-app VPN-профили доступны только системному IKEv2-VPN, стороннему приложению — нет.
- Один активный VpnService на пользователя → один tun; установка второго вызывает onRevoke.
- Per-app routing: allowlist **или** denylist (оба вместе → UnsupportedOperationException).
- Настоящая маршрутизация «разные приложения → разные туннели» на стоке = single-tun +
  userspace-роутер с UID-атрибуцией (`getConnectionOwnerUid`, API 29+, только TCP/UDP;
  INVALID_UID — отдельное состояние) и мультиплексингом на несколько апстримов.
- Поэтому «разные одновременные туннели» — это либо sing-box/mihomo (правила по package,
  не process_name), либо собственный роутер. Оба — отдельный этап, не текущий.

## 5. Вопросы ревьюеру

1. **Модель рейтинга**: сейчас «успешный домен» = сеть доступна (DNS+TCP+TLS) независимо от
   HTTP-кода; отдельно считаем «полный успех» (2xx/3xx) и «ограничено сервером» (401/403/429);
   лучший универсальный = максимум доступных доменов, плюс лучшие по категориям. Нужны ли
   веса/штрафы за latency, или как сейчас (последовательное сравнение по критериям ТЗ)?
2. **Смещение измерений**: порядок доменов перемешивается детерминированно (seed от индекса
   стратегии) — чтобы одинаковый набор стратегий сравнивался честно. Нужно ли дополнительно
   рандомизировать и seed (тогда повторы несопоставимы), или детерминизм + повторная проверка
   победителей оптимальны?
3. **Базовая линия**: сейчас нет замера «без обхода» (прямой канал). Стоит ли добавить в бенчмарк
   контрольный проход DIRECT, чтобы было видно, что именно даёт обход (иначе «успешные» домены
   могут быть успешными и без ciadpi)?
4. **Статистика**: 42 стратегии × 15 доменов × 3 попытки — сколько попыток нужно, чтобы
   отличить реальную разницу от шума, и как правильно отбирать итогового победителя
   (среднее по доменам, медиана, доля успешных)?
5. **Telegram в AUTO**: проверка DC из приложения (TCP-connect к 149.154.x/91.108.x) и переход
   на AWG/WARP — рабочая схема? Или правильнее предлагать пользователю встроенный
   прокси Telegram (SOCKS5/MTProxy) как отдельный режим?
6. **Что хранить как базу** для сравнения стратегий после обновлений ByeDPI/смены оператора:
   достаточно session/strategy/domain/attempt с типом сети и страной выхода, или нужно
   дополнительно хранить версию ciadpi, параметры MTU/endpoint и сырой SOCKS-лог?

# 2.0.8: Автовыбор лучшего WARP-профиля при деградации (Quality Manager для WARP)

Дата: 2026-11-18. Статус: **проектирование; не реализовано; 2.0.7 заморожена.**
Цель: заявленная пользователем доработка —
«автоматический подбор профиля warp: на главном экране постоянно показывает профиль 11;
нужно, чтобы автоматически подбирался лучший профиль, если выбранный профиль деградирует».

## Что уже есть (якоря в коде, читать перед реализацией)
- `warp/SeedCatalog.kt` — bundled seeds из `assets/seeds/warp_verified_seeds.json` (74 identity,
  `seed_order` 0..73), `DEFAULT_PROFILE_NUMBER = 11` (seed_order 10); метка «Профиль №N · WARP».
- `vpn/ConnectionManager.kt` — построение WARP-подключения: fallback от начала очереди seeds,
  «последний рубеж — профиль №11»; `prefs.lastGoodLabel`, `autoConnectOnce()`.
- `NetProbe` (через `ConnectionManager`) — exit probe через туннель (IP/страна). Используется
  после connect; готов для переиспользования в периодическом prober.
- `data/Prefs.kt` — `lastGoodLabel`, `connection_method`, `autoConnect`, `publicServerCountries` (паттерн
  «свежесть ≤7 дней, `CC@epoch`» — применим для метрик качества).
- `ui/home/HomeScreen.kt` — главный экран; профиль и пинг отображаются в шапке.
- `dpi/benchmark` — существующий паттерн SQLite-журнала измерений (переиспользовать для метрик).
- `auto_log.txt` — журнал причин переключения (писать туда «warp switch 11→23: 3/3 probes failed»).

## Термины и область
- «WARP-профиль» = bundled seed (в 2.0.8 под вопросом после решения о судьбе ключей) ИЛИ
  identity, зарегистрированный на устройстве через Cloudflare API (собственный генератор).
- Фича работает в транспорте **WARP** и в **AUTO** (как нижний уровень кандидатов).
- AWG и DPI **не затрагиваются**. Ручной пин AWG/DPI сохраняется полностью.
- Изменения только в WARP/AUTO-path и настройках; архитектуру VpnService/GoBackend не трогаем.

## Механика

### Пробер (идёт через туннель, own package → tun0)
- Запуск: пока VPN подключён, в существующем scope, вместе с app.
- Интервал по умолчанию **5 мин** (настройка: 1 / 3 / 5 / 10); пауза при «ru direct only» не требуется
  (пробу остаётся через tun0, пакет свой — проверено: own uid 10328 → tun0).
- Два независимых GET-запроса с таймаутом 5 с:
  1. `https://1.1.1.1/cdn-cgi/trace` — 200 + строка (лёгкая, Cloudflare);
  2. `https://www.gstatic.com/generate_204` — ожидаем 204 (Google).
- Меряется success + время полного ответа; любой из двух OK = цикл OK; оба FAIL = цикл FAIL.
- Не блокировать UI; результаты — в SQLite `warp_quality.db`:
  `quality(profile_id TEXT, ts INTEGER, success INTEGER, rtt_ms INTEGER, http_code INTEGER)`,
  хранить последние 60 записей на профиль.

### Метрики профиля (окно последних 5 циклов)
- `success_rate` = успешных / 5; `median_rtt` медиана RTT; `last_ts`.
- Профиль считается **degraded** при **3 последовательных FAIL** (`PROBE_FAIL_STREAK = 3`, по
  согласованию; настраиваемо 2/3/5)
  ИЛИ `success_rate < 0.5` за окно. RTT-деградация (RTT > 3× baseline) — сигнал для будущего, в v1 не переключает.
- Ручное подтверждение не требуется: переключение автоматическое (требование пользователя).

### Решение об переключении
- Только из WARP-семейства (bundled + зарегистрированные на устройстве).
- Порядок кандидатов: сначала самые свежие по `last_verified_at` (bundled) / собственные зарегистрированные,
  затем `success_rate` по убыванию, затем `median_rtt` по возрастанию; исключения внутри кандидатов:
  - деградировавший профиль — в `cooldown 30 мин`;
  - обратные переключения чаще, чем раз в **10 мин** (anti-flap);
  - профиль, недавно вышедший из cooldown, сначала 1 контрольная проба.
- После переключения: переподключение с новыми параметрами; запись в `auto_log.txt`:
  `warp-profile switch №11 → №23 (degraded: 3/3 probes; new exit <IP> <CC> rtt=NN мс)`.
- Новая страна выхода измеряется пробой (как сейчас), в UI — «≈ Страна (IP)».

### Взаимодействие с режимами
| Режим | Поведение |
|---|---|
| AUTO | WARP-кандидаты приобретают качество по тем же метрикам; переключение внутри WARP до перехода на другой транспорт; при устойчивой деградации ВСЕХ WARP-кандидатов — переход к следующему транспорту (существующая логика AUTO) |
| WARP (ручной) | Тумблер **«Автовыбор лучшего профиля»** (дефолт **ON** по запросу пользователя): автосмена при деградации, тумблер OFF = «использовать только этот профиль» |
| AWG / DPI | Фича неактивна |
| Пин профиля (долгое удержание по строке профиля → «Только этот») | Автосмена отключена для этого профиля; виден бадж «пин»; повторное действие снимает пин |

### UI и уведомления
- Главный экран: профиль + цветная точка качества
  (зелёная — здоров; жёлтая — завалил 1 пробу; красная — degraded), рядом RTT последней пробы;
  при смене по деградации — краткий Toast/уведомление
  «Профиль №11 деградирует → переключаюсь на №23 (3/3 проб)».
- Детали — в «WARP · тонкие настройки»: тумблер «Автовыбор лучшего профиля», интервал,
  «История переключений» (последние 10 из auto_log.txt), «Восстановить профиль» (снять cooldown).
- Раздел AUTO: автовыбор WARP-кандидатов указывается как нижний уровень кандидатов; настраиваемый порядок
  кандидатов (см. P3) остаётся первичным.

## Тест-план
1. Unit: агрегация метрик, DegradedOracle (streak/success_rate), выбор кандидата, anti-flap, cooldown.
2. Инженерная симуляция: принудительный probe fail (build-флаг/фейковый NetProbe) — смена происходит
   ровно после 3-го фейла, не раньше; не чаще 1 раз в 10 мин.
3. Устройство: профильный рубеж — переводить выходящие метрики в degraded намеренно (искусственная задержка/блокировка probe-URL на стороне сервера недоступна без root; допускается тестовый билд с фейковым prober).
4. Soak: 30 мин при включённом тумблере; проверка, что обычная деградация не сработала ложно на Tele2 5G;
   проверка смены при реальном падении №11 (редко; фиксируется toast + лог).
5. Проверка, что в режиме ADMIN (DPI)/AWG nothing changes.

## Оценка и порядок

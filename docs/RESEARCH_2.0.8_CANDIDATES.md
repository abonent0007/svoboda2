# «Свобода 2.0» — кандидаты для 2.0.8 (исследование, ничего не внедрено)

Дата: 2026-11-17. Источник: `confeden/Nova-Android`, отдельная лента `confeden/nova_updates`.
Проверено самостоятельно: `opera_endpoints.json` и `proton_nodes.json` — действительные
публичные файлы (opera обновлён 2026-11-17T14:43:14Z, "surfeasy-discover").

## Источники

1. **Opera endpoint feed** (`nova_updates/opera_endpoints.json`) — 14 публичных endpoint
   областей EU (5), AM (7), AS (2); видно как регион Americas (AM), не гарантия US-IP.
   Полезно только для отдельного Opera-транспорта через opera-proxy/surfeasy.
   Требует HTTP CONNECT/прочей логики `surfeasy` и НЕ является AWG/WARP-туннелем.

2. **Proton public nodes** (`nova_updates/nova_android/proton_nodes.json`) — 100 серверов
   по странам (CA13 CH8 JP12 MX9 NL12 NO8 PL6 RO8 SG12 US12). Только входы: IP, страна,
   город, public key сервера. Подключение требует собственной регистрации устройства
   в Proton VPN API (`/vpn/logicals?Tier=0`); иначе не подключиться. Это **отдельный
   транспорт**, не список для AWG.

3. **WARP verified seeds** (assets в Nova) — 50 IP:port endpoint, 45 IPv4 + 5 IPv6,
   15 разных приватных ключей (clients), один общий server public key, режим
   `warp-awg-exact`. Можно брать **только IP:port** в качестве кандидатов для нашего
   собственного `WarpProfileFactory`. Взять как есть нельзя: клиентские приватные ключи
   принадлежат Nova и их нельзя использовать в нашем приложении.

4. **DNS** — Yandex (`77.88.8.8`, `77.88.8.1`, `77.88.8.88`, `77.88.8.2`),
   Quad9/Google/Cloudflare дубли, `195.208.5.1` (RU, claimed) / `195.208.4.1` (unverified);
   DoH-эндоинты из RETIRED_BUILT_IN (автор Nova намеренно убрал) — не восстанавливать
   автоматически.

## Принцип (базовый)

- Публичные **данные** (endpoint, считаемые серверы) — можно брать как factual references.
- Чужие **идентичности** (клиентские приватные ключи Nova) — не берём.
- Лента Opera/Proton — материалы отдельного open-source проекта; использовать можно
  как публичные данные, атрибуция — в документации; переиспользовать их код не нужно.
- Ничего из этого не имплементируется до завершения 2.0.7.

## План (после решения о релизе 2.0.7)

1. (П1) Opera-транспорт: отдельный slot в AUTO с Surfeasy-прокси; endpoint pool из
   `opera_endpoints.json`; кэш 3 часа; проверка реального HTTPS через кандидата.
2. (П2) Proton: отдельный вариант туннеля через регистрацию собственной identity DES
   устройства (`/vpn/logicals?Tier=0`); оценить объём реализации; не смешивать с AWG.
3. (П3) WARP: расширить пул endpoint публичными IP из seeds, только как кандидаты
   для наших собственных WARP-генерированных профилей.
4. DNS: добавить Yandex DNS в каталог (с пометкой «только через RU-маршрут»), не вместо
   существующих; новые резолверы — только после замера на обеих сетях.

5. UI split-tunnel (безопасность пользовательской конфигурации):
   обнаружено 2026-11-18 — в ящике две похожие записи; строка «Пресет: Российские приложения»
   молча и полностью перезаписывает пользовательский профиль `russian_direct` (экран выбора,
   до 20+ пакетов) legacy-набором из 27 пакетов (`SplitTunnelPresets.russianApps`).
   В 2.0.8 обязательно:
   - визуально различать диалог каталога и legacy-пресеты (другие названия/иконки/цвет);
   - не делать молчаливую полную перезапись пользовательской конфигурации;
   - перед заменой — подтверждение с количеством добавляемых и удаляемых пакетов (diff);
   - предусмотреть откат предыдущей конфигурации;
   - предпочтительно — объединение системного пресета с пользовательскими исключениями
     (например, «добавить пресет» вместо «заменить профилем»).
6. WARP Quality Manager (автовыбор лучшего WARP-профиля при деградации) —
   полная спецификация: `docs/WARP_PROFILE_QUALITY_PLAN.md`.
   Суть: фоновая проба туннеля (собственные пакет → tun0), скользящие метрики по профилю,
   "degraded" = 3 FAIL подряд / success<0.5, автосмена лучшего кандидата (anti-flap 10 мин,
   cooldown 30 мин), в AUTO и в ручном WARP (тумблер «Автовыбор», дефолт ON), пин профиля,
   toast + auto_log.txt + точка качества на главном экране. Оценка 3–5 дней после релиза 2.0.7.
   Открытый подвопрос: судьба 74 bundled WARP-identity в assets (пользователь подтвердил
   генерацию им; после релиза — решить: вырезать keys из APK / оставить / только debug).
7. Data Plane Validation для AUTO (критично; без этого релиза быть не может) —
   инцидент: 2026-11-18, evidence: `docs/AUTO_FAIL_2026-11-18_evidence/`;
   полная спецификация исправления P0: `docs/P0_AUTO_FIX_SPEC.md`.
   Требования (архитектурные):
   - Трёхступенчатая машина состояний кандидата:
     TRANSPORT_UP (туннель/локальный прокси поднят) → DATA_PLANE_VALIDATING
     (проверка передачи DNS и HTTPS через выбранный транспорт) →
     PASS/HEALTHY (AUTO завершает выбор) | FAIL/DEGRADED (кандидат отклонён, следующий).
   - Две независимые HTTPS-пробы; именно через data-plane выбранного транспорта,
     не через случайный DIRECT-сокет приложения.
   - Провалившийся кандидат исключается из текущего цикла перебора.
   - Если кандидаты закончились — «Нет рабочего маршрута», а не ложный «Подключено».
   - Следующая попытка не должна сразу выбирать заведомо провалившийся endpoint
     сразу после истечения 5 минут (cooldown с записью отказа).
   - Anti-bounce НЕ может препятствовать переходу от нерабочего кандидата к следующему.
   - Причина отказа каждого кандидата — в auto_log.txt.
   - Различать ошибки: handshake / DNS / HTTPS / timeout endpoint.
   - Критерий приёмки: AUTO не имеет права показывать успешное подключение,
     пока data-plane не подтверждён.
   - Дополнительно: JobCancellationException (гонка отмены reconnect-корутины)
     не должен всплывать в пользовательском статусе — обрабатывать тихо, с записью в лог.
   - UI DEGRADED: экран «НЕТ ИНТЕРНЕТА» не имеет смысла «Повторить» (только «ОТКЛЮЧИТЬ»);
     «Повтор через Nс…» должен отражать реальную попытку подключения, а не антидребезг/заглушку;
     на этом экране нужен явный двойной CTA «Отключить | Повторить (следующий кандидат)».
   - Связь с п.6: один механизм Watchdog/Quality Manager, без конкурирующих переподключений.
8. P1 — Ручное управление Direct-приложениями (DIRECT App Picker) —
   уточнение состава (пользователь, 2026-11-18):
   - Показывать ВСЕ установленные приложения, включая системные.
   - Предустановленные пресетом DIRECT-пакеты скрывать из списка ручных добавлений
     (исключить дубликаты); пресет и пользовательский список — независимые источники.
   - Эффективный DIRECT-набор = пакеты активного пресета ∪ пользовательские исключения.
   - Смена пресета не теряет пользовательские исключения.
   - Удалённые приложения отфильтровываются при применении (pm.getPackageInfo, runCatching).
   - Применение — после переподключения VPN.
   - Хранение: отдельный StringSet (копия при чтении/записи), не пересекающийся с пресетами.
   - Launcher-список недостаточен для "всех приложений": для полного обзора нужен
     QUERY_ALL_PACKAGES; Play-политики его ограничивают, но дистрибуция GitHub Releases делает его приемлемым;
     риск и обоснование документировать; список приложений никуда не отправлять.
     Либо (альтернатива) — <queries> с нужными интентами + честная пометка «показаны приложения с лаунчером».
     Решить ДО реализации P1.
   - UI: поиск + мультивыбор (иконка/имя/пакет), счётчик, «Применить → переподключение».
   - Оценка: 0.5–1 день (без учёта проверки на устройстве).

## Этап: AUTO — 2026-11-18 (FAIL, NO-GO для 2.0.7)

См. `docs/AUTO_FAIL_2026-11-18_evidence/` (полные артефакты + таймлайн).

**AUTO FAIL — 18.11.2026, Tele2 LTE, Realme RMX3370.**
Причина: AUTO считает установление туннельного интерфейса достаточным условием успеха,
не проверяя доступность передачи пользовательских данных (data-plane) через выбранный маршрут.

Зафиксировано:
1. Кандидаты #1–#6 не подключились; причины отказов в журнале отсутствуют (только строки `try candidate #N`).
2. Кандидат #7 `public:any_1` создал туннельный интерфейс, но HTTPS и проверка IP не прошли
   (`IP недоступен · пинг не проходит`, экран «НЕТ ИНТЕРНЕТА»).
   После истечения anti-bounce AUTO повторно выбрал тот же кандидат (21:13:51) — цикл детерминировано возвращается к мёртвому endpoint.
3. Health-цикл (30 с) → 3 подряд неуспеха → backoff (2/5/10…с) → `autoConnect()` → тот же any_1:
   бесконечный цикл без смены кандидата; на экране «Повтор через 2с…» / «Повтор через 45с…».
4. Дополнительный брак, обнаруженный во время испытания:
   `JobCancellationException: StandaloneCoroutine was cancelled` всплывает в пользовательском
   статусе (состояние ОШИБКА, профиль переключился NL→FI).
5. Ручной WARP восстановлен «WARP · новый», HTTPS-probe OK (IP `2a09:bac5:5153:1478::20a:e0`, ping 89/97/105 мс);
   split-tunnel 20 пакетов russian_direct цел.
6. Требования к 2.0.8 (архитектурные): трёхступенчатая машина TRANSPORT_UP → DATA_PLANE_VALIDATING →
   PASS/HEALTHY | FAIL/DEGRADED; 2 независимые HTTPS-пробы через data-plane самого транспорта;
   исключение провалившегося кандидата из текущего цикла; «Нет рабочего маршрута» вместо ложного «Подключено»;
   anti-bounce не должен блокировать переход с мёртвого кандидата; причина отказа каждого кандидата — в auto_log.txt;
   автоопределение вида ошибки (handshake / DNS / HTTPS / timeout endpoint).
7. Решение (пользовательское): 2.0.7 — NO-GO до исправления и повторного теста AUTO.

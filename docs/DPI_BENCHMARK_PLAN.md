### 1.2. Критический вопрос ТЗ: гарантирован ли проход тестовых запросов через ciadpi?

**Да, и это проверено измерениями.**

Факты:
1. В DPI-режиме собственный пакет приложения исключён из VPN (`addDisallowedApplication`), т.к. ciadpi — отдельный процесс того же uid, иначе рекурсия. Проверено в `ip rule`: uid 10328 (наш) не попадает в `uidrange … lookup <vpn-table>`.
2. Локальный SOCKS5-сервер на `127.0.0.1:1080` — это **сам ciadpi**. Любой запрос из приложения через `127.0.0.1:1080` гарантированно проходит через ciadpi, а не мимо.
3. Проверено на устройстве: `SOCKS CONNECT 1.1.1.1:53 → OK`, `CONNECT www.youtube.com:443 → OK`, `CONNECT api.telegram.org → code 4` (Telegram-DC недоступны — совпадает с независимыми замерами).
4. Прямой (не-SOCKS) трафик приложения идёт мимо туннеля → **не годится** для измерения DPI. Значит: **все измерения бенчмарка — только через SOCKS5**.

Следствия для тестового клиента:
- DNS мерить **не** через DNS-over-TCP/UDP в туннеле: disorder-режим стратегии переставляет байты и портит DNS-ответ (проверено: ответ приходит переставленным, парсер падает). Вместо этого — SOCKS CONNECT с **доменом** (ATYP=3): ciadpi сам резолвит и в ответе SOCKS возвращает bound-address. Это и есть измерение DNS в DPI-режиме.
- TCP-шаг — SOCKS CONNECT с **IP-литералом** (уже разрешённым), чтобы не смешивать DNS и TCP.
- TLS-шаг — `SSLSocket` поверх SOCKS-сокета, SNI = домен, permissive TrustManager (фиксируем ошибки сертификата отдельно от факта TLS).
- HTTP-шаг — минимальный HTTP/1.1 GET по тому же сокету, парсинг status line; TTFB = время до первой строки статуса. Свежий сокет на каждую попытку (без пула OkHttp) → изоляция попыток и чистая задержка.

### 1.3. Что НЕ измеряется бенчмарком (важно, фиксируем в UI)

- Полный путь TUN → HEV(lwip) → ciadpi для «обычных» приложений: наш uid исключён из VPN, поэтому приложение не может ходить через туннель. Бенчмарк измеряет **эффективность стратегии ciadpi** (именно это и нужно ранжировать). Проверка end-to-end пути (включая lwip/MTU) — отдельная задача (P3 / DPI-1.5, см. §6).
- mapdns (HEV) при включённом туннеле резолвит домены сам (198.18.0.2 → пул 100.64.0.0/10). Измеряемый DNS в бенчмарке — резолв на стороне ciadpi. Для сопоставимости результатов фиксируем режим mapdns в логе сессии; при mapdns=ON расхождение ожидаемо и отмечается.

### 1.4. Известные грабли, найденные при анализе

- **ICMP непригоден**: shell/uid внутри VPN → ICMP уходит в туннель → SOCKS5 не переносит UDP → 100% потерь даже при живом интернете. Для бенчмарка — только TCP/TLS/HTTP.
- **Нет маршрута у исключённого uid** (случай на устройстве 2026-11-16): при двух LTE-сетях и «неправильном» дефолте netd таблица 99 пустеет → ciadpi не может выйти в интернет → приложение корректно показало «НЕТ ИНТЕРНЕТА»/DEGRADED. Диагностика, которую добавляем: различать «нет underlying-сети» (прямая проба нашего uid падает) и «стратегия не работает» (прямая проба проходит, SOCKS-проба падает). Это же — контрольный домен из ТЗ (п.10/11).
- Порядок в `ip rule`/`dumpsys connectivity` — источник истины для проверки, включения/исключения приложений.

## 2. Архитектура бенчмарка

```
ui/benchmark/DpiBenchmarkScreen.kt      ← выбор доменов / прогресс / итоги
dpi/benchmark/DpiDomainCatalog.kt        ← 47 доменов по 7 категориям (+ per-domain expected code)
dpi/benchmark/DpiBenchmarkStore.kt       ← SQLite: session / strategy / domain / attempt
dpi/benchmark/DpiDomainTester.kt         ← DNS→TCP→TLS→HTTP через SOCKS5 (сырые сокеты)
dpi/benchmark/DpiStrategyRunner.kt       ← цикл по стратегиям: смена ciadpi → замеры → запись
dpi/benchmark/DpiStrategyRanker.kt       ← рейтинг по правилам ТЗ §6
dpi/benchmark/DpiBenchmarkManager.kt     ← сессия, пауза/стоп, восстановление исходной конфигурации
```

### 2.1. Ключевое решение: перезапуск только ciadpi

ТЗ п.5: «если можно безопасно перезапускать только ciadpi — делать так». Можно:

- TUN/HEV остаются поднятыми (Android VPNService не трогаем, FGS не пересоздаём → нет системных разрывов);
- между стратегиями: `stopCiadpi()` → `startCiadpi(args следующей стратегии)` → ждём готовности SOCKS (порт принимает) → замеры;
- новых сокетов не остаётся: тестовые сокеты закрываем после каждой попытки, DNS-кэш приложения не используем (сырые сокеты, свой резолв через ciadpi).

Требуется маленький рефакторинг `DpiEngine`: выделить `startCiadpi(args: Array<String>): Boolean` и `stopCiadpi()` в отдельные публичные методы (сейчас они приватные и связаны с `start()`/`stop()`). Публичный API: `restartWithStrategy(id: String): Boolean` — без изменения поведения обычного подключения.

### 2.2. Изоляция стратегий (чистое состояние)

Перед каждой стратегией:
1. Закрыть все тестовые сокеты (клиент создаёт новый на каждую попытку — старых нет).
2. Остановить ciadpi, дождаться выхода процесса (`waitFor` + `destroyForcibly`).
3. Запустить ciadpi с аргументами стратегии, дождаться готовности порта (до 6 c, poll 250 мс).
4. Контрольная проверка: прямой TCP до 1.1.1.1:443 из приложения (наш uid, мимо туннеля) — «жива ли сеть вообще». Если нет → пауза сессии с явным статусом «нет сети», а не запись ошибок по стратегиям (ТЗ п.10).
5. Пауза 1 c (стабилизация), затем домены в перемешанном порядке (ТЗ п.2).

### 2.3. Попытки и успех

- 3 попытки на домен, интервал ~1 c.
- Попытка успешна, если DNS (domain-CONNECT) + TCP + TLS прошли и получен HTTP-ответ (любой код: 200/301/302/401/403/404 — код фиксируется, но **не** трактуется как блокировка; отдельно учитываем «ожидаемый» код домена).
- Домен считается доступным: ≥2 из 3 успешных попыток.
- 403 от Cloudflare — не блокировка (ТЗ п.5): фиксируем как `http_success=true, http_status=403`, в ожидаемых кодах помечаем как «анти-бот».
- Таймауты/reset/refused/DNS-ошибки различаются по типу.

### 2.4. Метрики

По каждой попытке: `dns_ok`, `resolved_ip`, `tcp_ok`, `tcp_ms`, `tls_ok`, `tls_ms`, `http_status`, `http_ok`, `http_ms` (TTFB), `error_type`, `error_message`.
По домену: медиана http_ms успешных попыток, min/max, success_rate.
По стратегии: successful_domains / failed_domains, success_rate, median_http_ms, median_tls_ms, error_count, тайминги.

### 2.5. Рейтинг (ТЗ §6, без сводного балла)

1. Количество доступных доменов — по убыванию.
2. Доля успешных попыток — по убыванию.
3. Медиана HTTP-задержки — по возрастанию.
4. Число timeout/reset — по возрастанию.
5. Медиана TLS-задержки — по возрастанию.

Рейтинги разделяются по типу сети (Wi-Fi / мобильная) — ключ в логе сессии.

### 2.6. Хранилище (SQLite)

`android.database.sqlite.SQLiteOpenHelper` (без новых зависимостей), БД `dpi_benchmark.db`:

- `test_session(session_id PK, started_at, finished_at, network_type, mapdns_enabled, selected_domains, total_strategies, completed_strategies, status, best_strategy_id, original_strategy_id, original_custom_args)`
- `strategy_test(test_id PK, session_id FK, strategy_id, strategy_name, strategy_args, started_at, finished_at, connected, successful_domains, failed_domains, success_rate, median_http_ms, median_tls_ms, error_count)`
- `domain_test(id PK, test_id FK, domain_id, domain, category, attempts, dns_ok, resolved_ip, tcp_ok, tcp_ms, tls_ok, tls_ms, http_status, http_ok, http_ms, retry_count, error_type, error_message)`
- `attempt(id PK, domain_test_id FK, attempt_no, dns_ok, resolved_ip, tcp_ok, tcp_ms, tls_ok, tls_ms, http_status, http_ok, http_ms, error_type, error_message)`

Плюс JSON/CSV выгрузка результатов (кнопка «Экспорт» → share intent).

### 2.7. Восстановление

- Исходная конфигурация (strategyId + customArgs + mapdns) снимается перед сессией и возвращается при «Стоп»/краше.
- Незавершённая сессия помечается `status='interrupted'`; при следующем запуске — предложение продолжить с последней завершённой стратегии (P2: полноценное возобновление).
- Кнопка «Пауза» — завершает текущую попытку, не стартует следующую стратегию; «Стоп» — останавливает всё и возвращает исходную конфигурацию.

## 4. План реализации

### P1 (в работе)
1. `DpiDomainCatalog` — домены, категории, ожидаемые коды.
2. `DpiDomainTester` — SOCKS5-клиент (сырой), фазы DNS/TCP/TLS/HTTP, 3 попытки.
3. `DpiEngine.restartWithStrategy()` — перезапуск только ciadpi (рефакторинг без изменения обычного пути).
4. `DpiBenchmarkStore` — SQLite-схема + CRUD.
5. `DpiStrategyRunner` + `DpiBenchmarkManager` — цикл, пауза/стоп, восстановление, запись.
6. `DpiStrategyRanker` — рейтинг + JSON/CSV.
7. UI: экран выбора доменов (чекбоксы, категории, «выбрать все/снять все/сбросить», счётчик, сохранение выбора) → экран прогона (прогресс, текущий домен, DNS/TCP/TLS/HTTP по шагам, пауза/стоп) → экран итогов (лучшая стратегия + кнопка «Применить эту стратегию» + полный рейтинг + экспорт).
8. Проверка на устройстве: Wi-Fi и 5G, ≥2 стратегии, воспроизводимость.

### P2
- Возобновление прерванной сессии.
- Раздельные рейтинги Wi-Fi/LTE (закладываем в P1 через `network_type`).
- Экспорт JSON/CSV (в P1 — базовый).
- Обработка потери сети (пауза, а не «всё ошибка») — базовая в P1.
- Проверка повторяемости (2 прогона одной стратегии).

### P3
- Сравнение сессий, история эффективности, авто-предложение лучшей стратегии.
- Отдельные наборы доменов (видео/AI/Telegram/веб) как пресеты.
- End-to-end проверка через TUN (требует защиты сокетов ciadpi — см. §6).

## 6. Что осталось за рамками P1 (честно)

- **Защита сокетов ciadpi от VPN** (нужна для end-to-end и для устойчивости): собственный пакет исключён из VPN, поэтому у ciadpi нет защищённых сокетов; при «неудачном» состоянии netd (две LTE-сети) его исходящие сокеты теряют маршрут. Варианты: (а) FD-passing (ciadpi передаёт fd сокетов в приложение, приложение вызывает `VpnService.protect(fd)`) — требует патча нашего вендоренного byedpi (MIT, ~150 строк); (б) in-process ciadpi с новым API остановки — тоже патч; (в) детект + честное сообщение (реализуется в P1). Это отдельная задача **DPI-1.5**, она же разблокирует end-to-end измерения и QUIC/UDP через SOCKS.
- **UDP/QUIC**: SOCKS5-ciadpi не переносит UDP → YouTube QUIC и голосовые — только TCP-часть. Учитывать в интерпретации результатов.

## 7. Критерии приёмки P1 (из ТЗ §13)

1. Пользователь вручную отмечает домены; выбор сохраняется между запусками. ✅ (дизайн)
2. Загружаются все 42 стратегии каталога. ✅ (DPI_CATALOG)
3. Каждая стратегия запускается отдельно (перезапуск ciadpi). ✅ (DpiStrategyRunner)
4. Предыдущая стратегия корректно останавливается перед следующей. ✅ (stop→wait→start→ready)
5. Все стратегии проверяют одинаковый набор доменов (порядок перемешивается). ✅
6. Для каждого домена сохраняются DNS/TCP/TLS/HTTP и задержки. ✅ (SQLite)
7. Ошибки не маскируются под успех (403 ≠ блокировка, но ≠ ошибка сети). ✅
8. Результаты в SQLite. ✅
9. Итоговый рейтинг формируется по §6. ✅
10. Лучшую стратегию можно применить вручную (кнопка «Применить» → сохранение + перезапуск DPI + проверка). ✅
11. Исходные настройки восстанавливаются при стоп/краше. ✅
12. Подтверждено на устройстве (Wi-Fi и 5G). ⏳ (после реализации)
